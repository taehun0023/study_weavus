単体テストは、JUnitを使用してサービスロジックを中心に作成しました。外部依存についてはMockitoで分離し、テスト対象のロジックを単独で検証しました。正常系・例外系・境界値のケースを、Given-When-Thenの構成でテストケースとして作成し、テスト結果はカバレッジツールで確認しました。

불량(버그) 대응

Q. 불량(버그)이 발생했을 때 어떻게 대응했나요?
불량이 발생했을 경우에는 먼저 불량 관리 엑셀 시트에 해당 불량이 어느 시나리오에서 발생했는지, 그리고 어떤 내용의 불량인지 정리해서 기록했습니다. 그 다음, 문제 원인을 파악하기 위해 Linux 환경에서 cat이나 tail 명령어로 로그를 확인했고, 어느 지점에서 어떤 이유로 에러가 발생했는지 분석했습니다. 원인이 되는 부분은 디버깅으로 소스 코드를 확인한 후 수정했고, 수정 후에는 JUnit으로 단위 테스트를 다시 실행하여 커버리지가 100%가 되는지 확인했습니다. 이후 로컬 환경에서 정상 동작을 확인한 뒤 운영 서버에 릴리스했습니다. 마지막으로 로직 재검토와 영향도 조사를 통해 다른 기능에 동일 문제가 없는지, 수정 영향이 없는지도 확인했습니다.

Q. 不具合（バグ）が発生した場合、どのように対応しましたか？
不具合が発生した場合は、まず不具合管理用のExcelシートに、どのシナリオで発生した不具合か、また不具合の内容を整理して記載しました。その後、原因を特定するために、Linux環境でcatやtailコマンドを使用してログを確認し、どの箇所で、どのような理由でエラーが発生しているかを分析しました。原因となる部分については、デバッグを行いソースコードを直接確認した上で修正対応を行い、修正後はJUnitで単体テストを再実行し、カバレッジが100％になることを確認しました。その後、ローカル環境で問題なく動作することを確認した上で、本番サーバーへリリースする形で対応しました。また、同様の不具合が他の機能でも発生する可能性がないかを確認するため、ロジックの見直しを行い、自分が修正した箇所が他機能に影響していないかについても影響調査を実施しました。

배치 처리 경험

Q. 배치 처리 경험에 대해 구체적으로 설명해 주세요.
1) 히타치 현장 + 파일배치
제가 담당했던 배치 처리는 파일 연계형 배치 프로그램이었습니다. 각 배치 클래스마다 입력 파일과 출력 파일이 명확하게 정의되어 있었고, 한 클래스에서 입력 파일을 받아 비즈니스 로직으로 데이터를 처리한 뒤, 그 결과를 출력 파일로 생성해서 다음 배치 클래스에 전달하는 구조였습니다. 다음 클래스에서는 이 출력 파일을 다시 입력 파일로 받아 처리했고, 비즈니스 로직을 적용한 후 데이터를 여러 파일로 분할해서 다음 단계의 여러 배치 클래스에 넘기는 방식으로 구현했습니다. 배치 실행과 스케줄 관리는 Hitachi JP1으로 했고, JP1 화면에서 배치 흐름이 정상 기동/연계/종료되는지 직접 확인했습니다. 배치 실행 후에는 입력/출력 파일과 로그를 확인해 정상 처리 여부와 에러 여부를 점검했습니다.

2) Spring Boot 배치
Java·Spring Boot·MyBatis를 사용해 DB 연계형 배치 처리 구현, 신규 기능 추가, 불량 대응을 담당했습니다. Spring Boot 환경에서 @Scheduled로 정해진 시간에 자동 실행되도록 구성했고, Job → Step → (ItemReader → ItemProcessor → ItemWriter) 구조로 설계했습니다. ItemReader에서는 MyBatis로 처리 대상을 조회했고, ItemProcessor에서 비즈니스 로직으로 처리 여부를 판단했습니다. ItemWriter에서는 JavaMailSender로 메일을 발송하거나, 잔여 좌석 해제는 상태 플래그 업데이트로 처리했습니다. 각 Step은 트랜잭션 단위로 관리해 예외 시 롤백되도록 했고, 불량 발생 시 로그 분석 후 수정 및 JUnit 재테스트로 정상 동작을 확인했습니다.

Q. バッチ処理の経験について具体的に教えてください。
1) 日立現場でのファイルバッチ処理経験
私が担当していたバッチ処理は、ファイル連携型のバッチプログラムでした。各バッチクラスごとに入力ファイルと出力ファイルが明確に定義されており、1つのクラスで入力ファイルを受け取り、ビジネスロジックでデータを処理した後、その結果を出力ファイルとして生成し、次のバッチクラスへ連携する構成でした。次のクラスでは、その出力ファイルを入力ファイルとして再度受け取り、ビジネスロジックを適用した上で、データを複数のファイルに分割し、次の段階の複数のバッチクラスへ渡す方式で実装しました。バッチの実行およびスケジュール管理にはHitachi JP1を使用しており、JP1の画面上でバッチが正常に起動しているか、前処理のバッチ終了後に次のバッチへ正常に遷移しているか、また途中でエラーなく全体の処理フローが維持されているかを直接確認していました。さらに、バッチ実行後にはサーバー上に生成された入力ファイル・出力ファイルおよびログを確認し、データが正しく処理されていることや、エラーが発生していないことも併せてチェックしていました。

2) Spring Boot バッチ処理
Java・Spring Boot・MyBatisを使用して、DB連携型バッチ処理の実装、新規機能追加および不具合対応を担当しました。バッチは Spring Boot 環境にて@Scheduledを使用し、定期的に自動実行されるように構成しました。処理構成はJob → Step →（ItemReader → ItemProcessor → ItemWriter）として設計し、ItemReaderでは MyBatis を利用してデータベースから処理対象データを取得しました。ItemProcessorでは、取得したデータにビジネスロジックを適用し、処理対象かどうかの判定を行いました。ItemWriterでは、メール送信バッチの場合は JavaMailSender を使用してメール送信を行い、残席解放バッチの場合はステータスフラグを更新する形で処理しました。各Stepはトランザクション単位で管理し、処理途中で例外が発生した場合でもロールバックされるように対応しました。また、不具合発生時にはログを分析して原因を特定し、ソース修正後にJUnitによる再テストを実施して、正常動作を確認しました。
